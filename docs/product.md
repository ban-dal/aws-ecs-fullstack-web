# 제품 기획

## 비전

AI를 활용해 기획·디자인·개발과 AWS 인프라 운영을 반복 가능하게 수행한다. 앱과 인프라는 별도 저장소에서 관리한다. 첫 제품은 방문자가 배포 환경을 확인할 수 있는 작은 Next.js 웹 앱이다. 핵심 성과는 복잡한 서비스 기능보다 PR에서 인프라 변경을 검토하고 두 실험 환경에 재현성 있게 배포하는 것이다. `prod`는 실제 고객용 운영 환경이 아니라 AI 성능 실험과 학습을 위한 두 번째 환경 이름이다.

## 사용자와 주요 흐름

| 사용자 | 원하는 일 | 완료 기준 |
| --- | --- | --- |
| 방문자 | prod에서 HTTPS로 앱 열고 ALB 뒤 응답 호스트 확인 | 페이지 로드와 `/api/health` 응답, 요청 경로·EC2 인스턴스·ECS 태스크 관측 |
| 개발자 | 로컬에서 기능 개발 | `pnpm dev`, 타입 검사, 빌드 가능 |
| 리뷰어 | 앱 PR의 동작 확인 | 타입 검사, 앱·arm64 이미지 빌드, health 확인 |
| 운영자 | preprod 확인 후 실험용 prod 승격 | preprod push 자동 배포, main 수동 실행과 승인 후 prod 배포 |

## 구현 범위

인프라 적용 상태와 운영 절차는 [인프라 저장소](https://github.com/ban-dal/aws-ecs-fullstack-app)를 본다.

- 실행 가능한 Next.js 앱, Node.js 22, pnpm workspaces, health API와 앱 CI.
- 홈의 요청 관측 대시보드. prod에서 접속 프로토콜, ALB 추적 헤더, 응답한 ECS 태스크·EC2 호스트·가용 영역을 표시하고 요청 표본을 비교한다. 이는 서비스 전체 상태 점검이 아닌 해당 브라우저의 요청 기록이다.
- 앱 PR의 타입 검사·빌드·컨테이너 health 확인.
- preprod 브랜치 push 시 이미지 빌드·배포, main에서 수동 실행과 승인 후 prod 배포.
- 환경별 VPC·ECR·ECS·VPN·ALB와 비용 운영은 인프라 저장소에서 관리한다.

## 현 단계 범위 밖

인증, 사용자 데이터베이스, 업로드 UI, CI에서 Lambda 함수 URL 공개, 멀티 리전 고가용성, 자동 비용 보증은 다음 단계로 남긴다. private subnet은 네트워크 경계를 학습하기 위해 생성하지만 NAT가 없어 현재 워크로드를 배치하지 않는다.

## 성공 조건

1. 로컬에서 앱을 실행하고 health 응답을 받는다.
2. 앱 PR에서 타입 검사·빌드·컨테이너 health를 확인한다.
3. preprod 브랜치 push 후 새 이미지를 VPN 내부 HTTP로 제공한다.
4. main의 수동 workflow를 승인해 prod HTTPS로 배포한다.

## 다음 결정

- 앱이 실제 데이터를 다루기 시작하면 데이터 모델, 저장소, 접근 제어, 개인정보 범위를 먼저 정의한다.
- 두 개 이상의 앱·공유 패키지가 생기고 빌드 시간 문제가 확인되면 Turborepo를 도입한다. 현재 pnpm workspace 구조는 그대로 유지할 수 있다.
- 실제 고객 데이터를 다루는 지속 운영으로 목적이 바뀌면 별도 AWS 계정 분리와 배포 IAM 권한 축소를 검토한다. 현재 실험 환경은 한 계정 안에서 분리하며 Free plan 크레딧을 유지한다.
